## 2. SYCL side

Device name is `SYCL0`; the oneAPI prelude must be sourced **in the same shell** as the
binary (`bench/configs/sycl-env.sh` does it). All `GGML_SYCL_*` are read in
`ggml/src/ggml-sycl/ggml-sycl.cpp:409-579` (`ggml_check_sycl()`); defaults are printed
at startup under `Running with Environment Variables:`.

### 2.1 CUDA graphs → SYCL graphs

* `GGML_SYCL_ENABLE_GRAPH` default **0** (`ggml-sycl.cpp:419`); the graph machinery is
  compiled only when `GGML_SYCL_GRAPH` is defined (`:489-493`), and this build has it
  (`GGML_SYCL_GRAPH=ON` in `CMakeCache.txt`). Capture path `:6436-6519`
  (`sycl_ex::command_graph`, `ext_oneapi_graph`).
* The upstream doc is blunt: *"Disabled by default because SYCL Graph is still on
  development, no better performance"* (`docs/backend/SYCL.md:803`). Sweep `S01` to
  check that claim on this box rather than trust it.

### 2.2 Tensor cores → XMX / DPAS

* The XMX (matrix-engine) path is the **XMX dequant-GEMM** used for MoE prompt
  processing: `GGML_SYCL_XMX_GATHER_TYPES` (bitmask of weight formats, default all),
  `GGML_SYCL_XMX_GATHER_SHAPES` (`joint_matrix` shapes, default 255),
  `GGML_SYCL_DYNAMIC_PRECISION` (operand type `F16`/`BF16`/`TF32`/`F32`; default `F16`
  with `GGML_SYCL_F16=ON`). Read at `ggml-sycl.cpp:431-436`; documented `SYCL.md:820-823`.
  The doc claims *"pp512 of Qwen3-30B-A3B UD-IQ3_XXS by about 50% on an Arc Pro B60"* —
  i.e. exactly this workload class. `S04` (`=0`) is the "tensor cores off" A/B; `S05`
  (`BF16`) is the precision trade.
* oneDNN is the default GEMM library (`GGML_SYCL_ENABLE_DNN` default 1, `:420`;
  `SYCL.md:809`) and oneMKL XMX FA activates for prefill when `-fa on`, quantized KV,
  `-b ≥ 1024`, prompt ≥ 1024 (`SYCL.md:813`). Our base uses `-b` default (2048) and
  `-fa` on with `q8_0` KV, so **`GGML_SYCL_ENABLE_MKL_FA` is live on the q35 base** —
  `S02` measures it.

### 2.3 Flash attention

`GGML_SYCL_ENABLE_FLASH_ATTN` (default 1, `:451`), oneDNN fused SDPA
`GGML_SYCL_FA_ONEDNN` (`:421`, `S03`), KV cap `GGML_SYCL_FA_ONEDNN_MAX_KV` (`:422`,
`S17` — the documented DEVICE_LOST mitigation for long context, `SYCL.md:811`), sparse
FA `GGML_SYCL_SPARSE_FA` (`:464`, `S12`). Same `-fa on` in the configs.

### 2.4 Pinned host memory + upload staging (matters most for `-ncmoe`)

* `GGML_SYCL_ENABLE_HOST_PINNED_MEM` default 1 (`:457-458`); the doc says **disable it when
  using `-lm mlock`** (`SYCL.md:804`) — our base does not mlock, so leave it on; `S09`
  is the A/B.
* `GGML_SYCL_UPLOAD_STAGING_SLOTS` default 4, "8 MiB pinned host slots … so the host copy
  of one slot overlaps the transfer of the previous one" (`:462`, `SYCL.md:806`) — this is
  the *model-load* path; `S08` raises it to 8. This is the closest analogue to CUDA's
  pinned-buffer staging for a host-expert MoE.
* `GGML_SYCL_HOST_PINNED_MEM_2G` (default 0, `:460-461`) exists to avoid the >2 GiB USM path
  that serializes H2D with compute (`SYCL.md:805`).

### 2.5 Device selection, free-mem query, immediate command lists, allocation limits

* `ONEAPI_DEVICE_SELECTOR="level_zero:0"` picks the dGPU (`SYCL.md:195,380-382`); the
  code reads it in `ggml/src/ggml-sycl/dpct/helper.hpp:915`.
* `ZES_ENABLE_SYSMAN=1` enables the free-VRAM query (`SYCL.md:828`); llama.cpp calls
  `zesInit` for it (`ggml-sycl.cpp:385-398`). Needed for `-ngl`/`--split-mode layer`
  placement decisions; `S18`.
* **Immediate command lists**: the Intel guide states the B580 is an **L0 V2 adapter
  which supports only immediate command lists**
  (<https://intel.com/content/www/us/en/developer/articles/guide/level-zero-immediate-command-lists.html>);
  the workaround `SYCL_PI_LEVEL_ZERO_USE_IMMEDIATE_COMMANDLISTS=0` was **removed** in the
  2024 DPC++ release notes and immediate lists are now the default. So `S16` is a probe
  expected to be a no-op or to error — documented, not recommended.
* `UR_L0_ENABLE_RELAXED_ALLOCATION_LIMITS=1` lets SYCL/UR allocations exceed 4 GiB
  (`SYCL.md:829,914-920`); llama.cpp's direct L0 path already requests the relaxed limit
  when `GGML_SYCL_USE_LEVEL_ZERO_API=1` (the default, `:439`).

### 2.6 AOT vs JIT and the persistent kernel cache

* Upstream: *"Missed the AOT (Ahead-of-Time) in building … The startup is slow (JIT) in
  first time, but subsequent performance is unaffected"* (`SYCL.md:870-872`).
* `SYCL_CACHE_PERSISTENT=1` + `SYCL_CACHE_DIR` cache the JIT binaries and speed **startup
  only**, and llama.cpp **warns against it** (stale/old code mixing → crashes; restore by
  deleting `~/.cache/libsycl_cache/`, `SYCL.md:922-934`). Both strings are present in
  `libsycl.so` (`strings`). `S15` measures it for the on-demand load case; keep it
  isolated.
* AOT would be a **build** change (`-fsycl-targets=…-sycldevice` / `examples/sycl/build.sh`),
  not a runtime knob — out of scope for the sweep, noted in §7.

## 3. Vulkan side

Everything below is read in `ggml/src/ggml-vulkan/ggml-vulkan.cpp`. Vulkan shaders are
compiled **AOT at build time** by `vulkan-shaders-gen` + `glslc`
(`ggml/src/ggml-vulkan/CMakeLists.txt:9,155-215`); the configure log confirms
`GL_KHR_cooperative_matrix`, `GL_NV_cooperative_matrix2`,
`GL_NV_cooperative_matrix_decode_vector`, `GL_EXT_integer_dot_product`, `GL_EXT_bfloat16`
are "supported by glslc". So there is **no runtime shader JIT** — the only startup cache
is ANV's SPIR-V→GEN pipeline cache (§3.3).

### 3.2 coopmat / coopmat2 on ANV — the "tensor cores" of the Vulkan backend

The detection is purely extension-name based (`ggml-vulkan.cpp:4039-4107`): coopmat2 is
enabled when the device lists `VK_NV_cooperative_matrix2` **and**
`GGML_VK_DISABLE_COOPMAT2` is unset (`:4063-4066`). `vulkaninfo` shows the B580's ANV
**does** advertise it, so on this box the Vulkan backend takes the coopmat2 paths:

* FA path selection `device->coopmat2 ? FA_COOPMAT2 : …` (`:1335`).
* `GGML_VK_DISABLE_COOPMAT2_DECODE_VECTOR` is a **no-op** because the decode-vector
  extension is not advertised (the `mmqid_bk` 64-vs-32 branch at `:1760` is therefore
  always the 32 path).

The A/Bs that matter are `V01` (coopmat2 off) and `V02` (KHR coopmat off); `V03`/`V04`/`V05`
disable the dot-product / bf16 accelerators.

## 4. Hardware side (the `xe` driver) — what needs root

All frequency and power files are root-owned, so **every hardware knob is a Marcel task**;
the read-only state is already optimal (see also `research/14-machine-tuning.md` §5).

| knob | path | current | writable by | Marcel command |
|---|---|---|---|---|
| freq ceiling | `…/tile0/gt0/freq0/max_freq` | 2850 (= rp0) | `644 root` | `echo 2850 \| sudo tee …/max_freq` |
| freq floor (clock-lock analogue) | `…/tile0/gt0/freq0/min_freq` | 1200 | `644 root` | `echo 2000 \| sudo tee …/min_freq` (pin the floor up) |
| power profile | `…/freq0/power_profile` | `[base] power_saving` | `644 root` | `echo base \| sudo tee …/power_profile` |
| power cap | `hwmon/hwmon4/power1_cap` | 200000000 (200 W) | `664 root:root` (user not in `root` group) | `echo 190000000 \| sudo tee …/power1_cap` |
| throttle state | `…/freq0/throttle/reasons` | `none` | read-only | — |
| ReBAR | `resource2` 16 GiB prefetchable, `resource2_resize=0x7f00` | active, max | read-only | already optimal |
| PCIe link | platform-facing `00:01.1↔01:00.0` = **Gen4 x8** (the `2.5 GT/s x1` lines are the on-card switch's advertised capability) | max | read-only | already optimal |
| GuC / HuC | `journalctl -k`: GuC 70.72.1, HuC 8.2.10, DMC v2.6 | current | firmware dir is root | update only if a newer `bmg_guc_70.bin` ships |
| `xe` module params | `/sys/module/xe/parameters/` (e.g. `vram_bar_size` unset) | defaults | root/module | — |

**Recommended experiments for Marcel (none applied):**

1. Raise the frequency floor to remove the 1200↔2850 ramp latency between tokens:
   `echo 2000 | sudo tee /sys/class/drm/card0/device/tile0/gt0/freq0/min_freq`.
   This is the real "clock lock" — the card already reaches rp0 under load
   (`act_freq` 2850, `throttle/reasons=none`), so the gain is ramp, not ceiling.
2. Set the power profile to `base` if it ever drifts to `power_saving` (it is already
   `[base]`), and leave `power1_cap` at 200 W (above the B580's 190 W TBP).
3. There is **no persistence-mode equivalent to set** — the `xe` driver keeps GuC/HuC
   resident; nothing to do.

## 6. What is already optimal / a no-op on this box (do not sweep)

* `GGML_VK_DISABLE_COOPMAT2_DECODE_VECTOR` — decode-vector not advertised (no-op).
* `GGML_VK_ENABLE_MEMORY_PRIORITY` — `VK_EXT_memory_priority` not on the B580 (no-op).
* `GGML_VK_DISABLE_OCP_FP4` — microscaling extension not advertised (no-op).
* `SYCL_PI_LEVEL_ZERO_USE_IMMEDIATE_COMMANDLISTS=0` — B580 is L0 V2, immediate-only.
* GPU clocks/power/PCIe/ReBAR — already at max / no throttle (research/14 §5).
* Persistence mode — nothing to set on `xe`.

## 7. Honest gaps

* **SYCL on Qwen3.6-35B-A3B is expected broken**: known bad output on B580 for
  `qwen35moe` (upstream #28728, `research/02`, `research/13` §3.5). The `S*` configs exist
  and lint clean, but a first SYCL row must **prove correctness**, not just speed, before
  any `S*` number is trusted. The Vulkan `V*` block has no such caveat.
* Nothing measured here — no model loaded, no benchmark run.
* AOT for SYCL is a build change (`-fsycl-targets`), not a runtime knob; the persistent
  JIT cache (`S15`) is the only runtime startup lever and upstream discourages it.
* `V16`/`V17`/`S15`/`S08` move **startup/load** time; measure them with
  `matrix-server.sh`'s cold/warm `startup` rows, not with `llama-bench` pp/tg.
* The `V08` oversubscribe path wedged the driver once (`research/10`); run it last and
  with `free=` headroom noted.
