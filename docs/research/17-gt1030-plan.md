### 1.2 ⚠ Kernel 7.2 build break — VERIFIED on this exact kernel, PKGBUILD has no fix

Read directly from `/usr/lib/modules/7.2.5-3-omarchy/build/include/`:

- `linux/string.h` — **`strncpy` prototype is gone** (only comments mention it); `strscpy` present.
- `drm/drm_atomic.h` — **`struct drm_atomic_commit`**, `drm_atomic_commit_alloc` — the old `drm_atomic_state` spelling is renamed.
- `linux/of_gpio.h` — absent (that was the 7.0/7.1 break; not the 7.2 one).

The 580 driver still calls `strncpy` in `nvidia-modeset-linux.c` and probes
`drm_atomic_state` in `conftest.sh`. On kernel 7.2 this fails exactly as reported
(hive article on 580.142 + XanMod 7.2.4; CachyOS ships a 7.2 patch for the 580/615 tree).
**The current AUR `nvidia-580xx-utils` PKGBUILD applies only two patches**
(`0001-Enable-atomic-kernel-modesetting-by-default`, `0002-Fix-hardware-cursor-crash`) — **no 7.2
patch**. So the DKMS build is expected to fail on `7.2.5-3-omarchy` unless 580.178.04
happened to upstream the fix. The install output will say so immediately
(`Error! Bad return status for module build on kernel: 7.2.5-3-omarchy`).

**Fallback — two header edits** (adapted from the hive article + the canonical CachyOS
`0001-make-Add-support-for-7.2-Kernel.patch`, which is written against `kernel-open/` paths; the AUR
package instead copies the `.run`'s proprietary `kernel/` tree into `/usr/src/nvidia-580.178.04`,
so the paths below are `common/…` and `nvidia-drm/…`):

```sh
# run ONLY if the dkms build failed with strncpy / drm_atomic_state errors
SRC=/usr/src/nvidia-580.178.04
ls "$SRC"          # expect: common/  nvidia/  nvidia-drm/  nvidia-modeset/  nvidia-uvm/

# 1. ONE global strncpy fallback. `common/inc/nv-time.h` is included by every sub-module, so this
#    covers every strncpy call site (core, modeset, drm, uvm) in a single edit — do NOT sed each
#    file, and do NOT swap in strscpy (it returns ssize_t, not char*).
sudo tee -a "$SRC/common/inc/nv-time.h" >/dev/null <<'EOF'

#include <linux/version.h>
#if (LINUX_VERSION_CODE >= KERNEL_VERSION(7, 2, 0))
static inline char *strncpy(char *dest, const char *src, size_t count)
{
    char *tmp = dest;
    while (count) { if ((*tmp = *src) != 0) src++; tmp++; count--; }
    return dest;
}
#endif
EOF

# 2. drm_atomic_state -> drm_atomic_commit shim, injected after the kconfig include in
#    nvidia-drm-conftest.h (anchor is the line the CachyOS patch keys on).
sudo sed -i 's|#include <linux/kconfig.h> // for IS_ENABLED()|&\n\n#include <linux/version.h>\n#if LINUX_VERSION_CODE >= KERNEL_VERSION(7, 2, 0)\n#define drm_atomic_state                 drm_atomic_commit\n#define drm_atomic_state_alloc           drm_atomic_commit_alloc\n#define drm_atomic_state_init            drm_atomic_commit_init\n#define drm_atomic_state_clear           drm_atomic_commit_clear\n#define drm_atomic_state_default_clear   drm_atomic_commit_default_clear\n#define drm_atomic_state_default_release drm_atomic_commit_default_release\n#define drm_atomic_state_put             drm_atomic_commit_put\n#define NV_DRM_CRTC_ATOMIC_CHECK_HAS_ATOMIC_STATE_ARG\n#define NV_DRM_PLANE_ATOMIC_CHECK_HAS_ATOMIC_STATE_ARG\n#endif|' \
  "$SRC/nvidia-drm/nvidia-drm-conftest.h"

sudo dkms build nvidia/580.178.04 -k 7.2.5-3-omarchy && sudo dkms install nvidia/580.178.04 -k 7.2.5-3-omarchy
```
If the `sed` anchor doesn't match (the file may differ slightly), just paste the `#include
<linux/version.h>` + `#if` … `#endif` block near the top of `nvidia-drm-conftest.h` by hand — it
only needs to precede the DRM sources that use `drm_atomic_state`. Source:
`github.com/CachyOS/CachyOS-PKGBUILDS/blob/master/nvidia/nvidia-utils/0001-make-Add-support-for-7.2-Kernel.patch`.

### 1.4 mkinitcpio / Limine — no config change needed (and why)

`HOOKS=(… kms …)`, `MODULES=()`. The `kms` hook adds modules under `/drivers/gpu/drm/`
(`/usr/lib/initcpio/install/kms`), so it currently embeds `nouveau.ko` (which is in the kernel
tree at `kernel/drivers/gpu/drm/nouveau/`). DKMS installs the nvidia modules to
`kernel/drivers/video/`, which the `kms` hook does **not** match — so **nvidia is not pulled into
the initramfs**. That is the desired outcome: no early KMS, no `MODULES=(nvidia …)` line (which
would break hibernation, and this box has `resume=` in `/proc/cmdline`), and no risk to the
B580-driven boot. The stale `nouveau.ko` in the image is harmless (blacklisted).

Initramfs is a **UKI built by Limine**, not by a preset: rebuild with `sudo limine-update`
(the pacman hook `/etc/pacman.d/hooks/90-mkinitcpio-install.hook` runs it automatically when the
DKMS module lands). Limine also exposes **Snapshots** boot entries (limine-snapper-sync) as a
belt-and-braces rollback.

## 2. Task B — CUDA 12 toolkit (root-free) + llama.cpp CUDA cc-61 build

### 2.1 Why 12.9 and not 13

CUDA **13.0** removed offline compilation for cc < 7.5 (Maxwell/Pascal/Volta) — confirmed by
NVIDIA's developer blog and gpucompat.com ("Pascal 6.0/6.1/6.2 — newest CUDA that targets it:
**12.9** — removed in 13.0"). Driver 580 is the LTS branch shipped *with* CUDA 13.0 and is
supported to mid-2028, so a 12.9-built binary runs on the 580 driver. **Build with 12.9; run on 580.**

### 2.2 Toolkit options — pick one

| Route | Root? | Verdict |
|---|---|---|
| **AUR `cuda-12.9`** (pkgver **12.9.2**, `_driverver 575.57.08`) | yes | **Recommended.** Real Arch package, installs `/opt/cuda`, `depends=('gcc14' 'opencl-nvidia' 'nvidia-utils')`, symlinks `/opt/cuda/bin/gcc → /usr/bin/gcc-14`, and carries `fix-glibc241.patch` + `fix-glibc242.patch` + the CCCL #4972 patch. Description literally: *"version 12.9 (Maxwell/Pascal/Volta support)"*. |
| Root-free runfile | no | `sh cuda_12.9.2_575.57.08_linux.run --silent --toolkit --toolkitpath=$HOME/cuda/cuda-12.9.2 --override --no-man-page` (5.88 GB, `content-length: 5877673931`). **Blocked on the host compiler**: nvcc 12.9 supports gcc ≤ 13; this box has only gcc 16.2.1 / clang 22.1.8, so it needs `--allow-unsupported-compiler` and is likely to fail on gcc-16 headers. Not recommended. |
| pip `nvidia-cuda-*-cu12` wheels | no | Fiddly: the wheel layout (`nvidia/cuda_nvcc`, `nvidia/cublas/lib`) is not a `FindCUDAToolkit` root; needs a hand-merged prefix. Skip. |
| conda | no | conda/mamba not installed. Skip. |

(glibc 2.44 is newer than the 2.41/2.42 the PKGBUILD patches for; if `/opt/cuda` binaries fail to

### 2.4 Exact cmake line — one binary, Vulkan **and** CUDA

`ggml` builds a backend registry that registers/loads multiple backends
(`ggml/src/ggml-backend-reg.cpp`: `register_backend` / `load_backend`); the CUDA and Vulkan
options are independent (`ggml/CMakeLists.txt` L199 `GGML_CUDA`, L224 `GGML_VULKAN`), and the
documented example is `-DGGML_CUDA=ON -DGGML_VULKAN=ON`. So **yes, one binary carries both**, and
`--list-devices` will show `Vulkan0` (B580), `Vulkan1` (GT 1030 via the NVIDIA ICD), `Vulkan2`
(iGPU) and `CUDA0` (GT 1030).

```sh
source /etc/profile.d/cuda.sh
CUDA_TIP=/home/nexuslink/NEXUS_AI_CENTER/LOCAL-AI-LAB/engines/llama.cpp-cuda-tip
cmake -S "$CUDA_TIP" -B "$CUDA_TIP/build" -G Ninja -DCMAKE_BUILD_TYPE=Release \
  -DGGML_VULKAN=ON -DGGML_CUDA=ON \
  -DCMAKE_CUDA_ARCHITECTURES=61 \
  -DCMAKE_CUDA_HOST_COMPILER=/usr/bin/g++-14

flock -s /home/nexuslink/NEXUS_AI_CENTER/LOCAL-AI-LAB/bench/.gpu.lock \
  cmake --build "$CUDA_TIP/build" -j 20
```

Notes / fallbacks:
- `CMAKE_CUDA_ARCHITECTURES=61` overrides ggml's `native` default (`ggml/src/ggml-cuda/CMakeLists.txt` L21/L41); ggml already documents `61 == Pascal, __dp4a`. Building `61` only also means **no GPU is needed at build time** (no driver probe) — the build can run before/without the reboot.
- `CMAKE_CUDA_HOST_COMPILER` is belt-and-braces; the AUR package's `/opt/cuda/bin/gcc → gcc-14` symlink already makes nvcc pick gcc-14 once `cuda.sh` is sourced.
- Default `GGML_CUDA_FA_QUANTS` (`q4_0-q4_0;q8_0-q8_0;f16-f16;bf16-bf16`) already covers the `-ctk/-ctv q8_0` the bench harness uses — no `GGML_CUDA_FA_ALL_QUANTS` needed.
- If the CUDA backend faults at runtime on Pascal, retry with `-DGGML_CUDA_NO_VMM=ON`.
- Verify: `build/bin/llama-cli --list-devices` must show `CUDA0: NVIDIA GeForce GT 1030 (2047 MiB, …)`.

### 2.5 ⚠ Cross-backend caveat (honest limit)

Two cards in one process works **by task**, not by splitting one model:
- ✅ main model on `Vulkan0` + vision projector on `CUDA0` (`--mmproj-device`)
- ✅ main model on `Vulkan0` + draft model on `CUDA0` (`--spec-draft-device`)
- ❌ one model's layers split across `Vulkan0`+`CUDA0` (`-sm layer`) — layer/row split assumes one
  backend family; don't try to pool the two cards' VRAM for a single model.

## 3. Task C — ranked jobs for the GT 1030

The card is **weak** (48 GB/s, below the box's dual-channel DDR5; no tensor cores; 2 GB). So the
value is **not speed** — it is (a) freeing B580 VRAM, (b) running a second small model
concurrently, (c) taking a bursty CPU job. Ranked by that:

### C1 — ⭐⭐⭐ mmproj (vision projector) on the GT 1030 → frees B580 VRAM
- **Benefit:** an mmproj is 0.4–1.3 GB resident on the B580 for the whole session; moving it to the
  GT 1030 returns that VRAM to the main model (matters on a 12 GB card).
- **Evidence it's supported:** `common/arg.cpp:2613` defines `-mmdev / --mmproj-device` ("device to
  use for multimodal projector … default: follows --device"), and `tools/mtmd/mtmd.cpp:612` passes
  `ctx_params.device` into the clip model loader — a genuinely separate device handle.
- **Steps:** build §2.4, then
  `llama-server -m <main.gguf> --mmproj <mmproj.gguf> -dev Vulkan0 -mmdev CUDA0 -ngl 99 …`
- **Verdict:** best value. Needs the combined binary; test one image to confirm the cross-backend
  clip path works (the flags exist, cross-backend use is not something this box has run yet).

### C2 — ⭐⭐ upgrade the embedding model onto the GT 1030 (quality, not speed)
- **Reality check:** Hindsight `local_embedded` embeddings are **not on the B580 at all** — they run
  in-process on `sentence-transformers 6.1.0` + **`torch 2.14.1+cpu`**, default model
  `BAAI/bge-small-en-v1.5` (`hindsight_api/config.py:1212`). So moving them "off the B580" frees
  nothing; it only frees CPU.
- **Supported CUDA knobs (read from the installed package):** `HINDSIGHT_API_EMBEDDINGS_ONNX_DEVICE`
  + `HINDSIGHT_API_EMBEDDINGS_ONNX_CUDA_DEVICE_ID` (ONNX provider on a chosen CUDA device), and
  `HINDSIGHT_API_EMBEDDINGS_LOCAL_FORCE_CPU` (unset → sentence-transformers would use CUDA if torch had it).
- **Real value:** the GT 1030 can host a *bigger* embedding model than bge-small (e.g.
  Qwen3-Embedding-0.6B, ~640 MB Q8 fits 2 GB) for better recall — as a separate CUDA llama.cpp
  embedding server. But Hindsight exposes no embedding-endpoint URL (only an LLM base_url), so this
  needs either the ONNX-provider route + `onnxruntime-gpu` (CUDA 12 + **cuDNN 9.10**, since 9.11
  dropped Pascal; AUR `cudnn9.10-cuda12.9` exists) or patching Hindsight to call the endpoint.
- **Verdict:** medium. bge-small on CPU is already fine; only pursue if you want a larger embedder.

### C3 — ⭐⭐ draft model for speculative decoding on the GT 1030
- **Evidence:** `common/arg.cpp:4248` defines `--spec-draft-device / -devd / --device-draft`
  ("devices to use for offloading the draft model … default: follows --device"), plus `-md / --model-draft`.
- **Fit:** a 2 GB budget caps the draft at ~0.5–1.5 B params (e.g. Qwen3-0.6B Q4 ≈ 400 MB) and it
  must share the target's tokenizer. Cross-device speculative decode adds a sync hop per step.
- **Steps:** `llama-server -m <target> -dev Vulkan0 -md <draft.gguf> -devd CUDA0 -ngl 99 --draft-max N …`
- **Verdict:** medium — measure; the 48 GB/s draft card may not keep up, and acceptance rate decides it.

### C4 — ⭐ rendering desktop clients (Quickshell / Qt) on the GT 1030 → frees ~740 MiB B580
- **What actually holds the VRAM:** Hyprland ≈554 MiB + Quickshell ≈183 MiB (measured, `arc-vram.py`).
- **Why it's hard:** Quickshell is a Wayland layer-shell client. Its frames are dma-bufs imported and
  composited by **Hyprland on the B580**; rendering them on a different GPU requires cross-GPU
  dma-buf import, which is exactly what failed on nouveau. Mesa's `DRI_PRIME` doesn't select the
  proprietary NVIDIA render node, and `__NV_PRIME_RENDER_OFFLOAD`/`__GLX_VENDOR_LIBRARY_NAME=nvidia`
  are X11/GLX-offload mechanisms, not native-Wayland compositor clients.
- **If you want to try (expect failure):** `DRI_PRIME=pci-0000:08:00.0 QSG_RHI_BACKEND=vulkan quickshell …`
  — but the compositor still owns presentation on the B580.
- **Verdict:** lowest — a Wayland client can't move its own presentation off the compositor's GPU.
  Leave parked (matches the 00-plan.md "parked" note).

### C5 — ⭐ Parakeet STT on the GT 1030 (CUDA) instead of CPU
- **Current state:** Voxtype `engine="parakeet"`, model `parakeet-unified-en-0.6b` (int8 ONNX,
  `~/.local/share/voxtype/models/`), a **source build** whose compiled features are
  `parakeet, moonshine, sensevoice, paraformer, dolphin, omnilingual, cohere, openvino` — **no CUDA**.
- **Supported path:** voxtype's `Cargo.toml` has `parakeet-cuda = ["parakeet","parakeet-rs/cuda"]` and
  `onnx-cuda-enabled = ["ort/cuda"]`; `voxtype setup gpu --enable` / `--gpu-device` exist, and
  `voxtype info accel` reports the backend. So it *is* a real feature.
- **Cost:** rebuild `~/build/voxtype` with `--features parakeet-cuda`, which pulls `onnxruntime-gpu`
  (CUDA 12 + cuDNN; Pascal needs **cuDNN 9.10**, AUR `cudnn9.10-cuda12.9`).
- **Verdict:** lowest — a 0.6 B int8 model on a 48 GB/s, tensor-core-less card is unlikely to beat
  the 7900X's AVX-512 CPU, and it's the most build effort. Skip unless CPU latency ever annoys.

### Ranking summary

| # | Job | Frees B580 VRAM | Effort | Verdict |
|---|---|---|---|---|
| C1 | mmproj on CUDA0 | ~0.4–1.3 GB | low (flag) | **do first** |
| C2 | bigger embedding model on CUDA0 | ~0 (CPU→GPU) | med | only for embed quality |
| C3 | draft model on CUDA0 | ~0 (adds use) | low (flag) | measure |
| C4 | Quickshell/Qt render offload | ~740 MiB | high | parked / not viable |
| C5 | Parakeet STT on CUDA | ~0 (CPU→GPU) | high | skip |

## 4. Post-reboot side effects to check (Hyprland / Vulkan)

### 4.1 Vulkan device index order — `--device Vulkan0` must still be the B580
The NVIDIA ICD adds `nvidia_icd.json` to `/usr/share/vulkan/icd.d/`. The loader enumerates ICD
manifests in directory (alphabetical) order — currently `intel_hasvk`, `intel`, `radeon`; after
install: `intel_hasvk`, **`intel`**, **`nvidia`**, `radeon`. So the expected order is
**Vulkan0 = B580, Vulkan1 = GT 1030, Vulkan2 = iGPU** — i.e. `Vulkan0` should *not* move. **Verify
it**, because every bench config and the live server pin `--device Vulkan0`:

```sh
/home/nexuslink/NEXUS_AI_CENTER/LOCAL-AI-LAB/engines/llama.cpp-vulkan-tip/build/bin/llama-cli --list-devices
# expect: Vulkan0 = Intel(R) Arc(tm) B580 Graphics ...
```
If the B580 is no longer `Vulkan0`, **lock it** by hiding the other ICDs for that process:
```sh
export VK_DRIVER_FILES=/usr/share/vulkan/icd.d/intel_icd.json    # B580 only -> guaranteed Vulkan0
```
(Add that export to the bench harness / server unit rather than editing every config.)

### 4.2 Forcing Proton/DXVK games to the B580
DXVK prefers *a* discrete GPU, but the GT 1030 is also `DISCRETE_GPU` — with two discrete cards the
choice is no longer obvious, and the GT 1030 is the wrong one. Pin by device name in the Steam
launch options (name comes from `vulkaninfo`):
```
DXVK_FILTER_DEVICE_NAME="Intel(R) Arc(tm) B580 Graphics" %command%
```
`DXVK_FILTER_DEVICE_NAME` matches a substring and takes the first match; `DXVK_FILTER_DEVICE_UUID`
is the precise alternative. If a title still misbehaves, hide the NVIDIA ICD for the game process
with `VK_DRIVER_FILES=/usr/share/vulkan/icd.d/intel_icd.json` (also removes the card from the
VKD3D-Proton device list). `MESA_VK_DEVICE_SELECT` does **not** apply here — that is a Mesa/RADV
selector, and the NVIDIA card is not a Mesa driver.

### 4.3 Hyprland primary
`AQ_DRM_DEVICES` (Intel first, stable by-path) already keeps the compositor on the B580; confirm
with `hyprctl systeminfo` after reboot and `hyprctl monitors` still shows all three monitors on the
Intel card. `__GLX_VENDOR_LIBRARY_NAME=mesa` in `hyprland.lua` should stay.
