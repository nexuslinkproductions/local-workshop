## Per-engine notes

**ninfer-offload (item 1) — CONFIRMED CUDA-only, unusable on Arc.** The fork README states requirements plainly: "NVIDIA RTX 40-series (sm_89) or RTX 5090 (sm_120a). RTX 30-series and older are not supported." Build is `-DCMAKE_CUDA_ARCHITECTURES=89`, host toolchain "Linux, CUDA 12.8 or newer, GCC 13". There is no SYCL, Vulkan, ROCm, XPU, OpenCL or Metal mention anywhere in the README [1]. Mechanism: `--moe-offload` keeps routed experts in host RAM (AVX2 row-split CPU kernels), router/shared-expert/attention/GDN/head/KV on GPU, with a configurable GPU replica count and an LRU expert cache (`--moe-gpu-experts`). It uses its **own `.ninfer` conversion**, not GGUF (converts the 354 GB BF16 checkpoint from HF/ModelScope). It does ship `ninfer-serve` (OpenAI + Anthropic APIs). Reported numbers are on RTX 4060 Ti 16 GB (19.2–24.1 tok/s for Flash-Next with 64 GPU experts) [1]. Verdict: **deny usability on Arc** — CUDA silicon + driver required, nothing ported.

**vLLM CPU/XPU (item 2) — yes, there is an Intel XPU backend, and CPU offload works for MoE but is not expert-aware by default.** vLLM has a first-class Intel XPU backend (V1 engine; TP via oneCCL, single-node PP, DP and EP for MoE; Intel maintains optimized images and "actively contributes upstream") [S1]. Its offload is the generic `--cpu-offload-gb` / `--cpu-offload-params` (UvaOffloader), which is **not** an expert cache: the vLLM forum answer states all experts must be resident (GPU or CPU) at startup and the needed weights are streamed H2D per inference — "on-demand or JIT expert loading is not currently supported" [S2]. The killer detail, fetched directly: on **Intel XPU** with Qwen3.8-Flash-Next, `--cpu-offload-gb 47` gives **4.26 tok/s** with default eviction order but **9.46 tok/s** with `--cpu-offload-params experts`, because the default offloader walks `named_parameters()` and evicts the *hottest* (dense) weights first [3]. So CPU offload "works" for MoE on XPU but you must pass `--cpu-offload-params experts` or lose ~2.2×. Caveat: vLLM XPU MoE quantization is broken — INC returns `UnquantizedFusedMoEMethod` for every MoE layer on XPU ("XPU and CPU do not support MoE quantization yet"), so an int4 MoE checkpoint materializes as bf16 (~60 GB) and OOMs; the OOM then presents as an `empty_cache` livelock on a 31 GB Arc Pro B70 [4]. Net: XPU backend real, CPU offload real but crude, XPU MoE quant path fragile. Not GGUF (safetensors).

**llama.cpp expert-offload forks (item 3) — only two have Arc-relevant paths, and the Arc one is a negative result.** Searched GitHub for MoE expert-offload forks:
- **da3dsoul/Qwen3.8-Flash-Next-LlamaCpp-MoE-Cache-Arc-Experiments** — the only fork that explicitly targets Arc: it ports a CUDA MoE expert-cache design to **llama.cpp's SYCL backend on an Arc Pro B70** for Qwen3.8-Flash-Next (`qwen4exp`). Headline finding is negative: "the custom SYCL MoE expert cache was built, works, and is correct — but it only ties, not beats, plain `-ncmoe` static CPU/GPU expert placement (a stock upstream flag, zero custom code)." They reverted to stock `-ncmoe` as production default [7]. So there is no fork advantage to chase here; stock llama.cpp `-ncmoe` is the SYCL/Arc answer.
- **Xtopia5616/llama.cpp-vulkan-b390-tuned** — Vulkan (+SYCL) fork tuned for **Arc B390**; includes "MoE route skipping, routed-row packing, expert compaction, and device-resident route/cache support" [8]. Measured on B390 + Qwen3.6-35B-A3B IQ3_XXS: tg128 34.21 → 37.68 tok/s (v1 vs baseline), vulkan0 [8]. It is a B390-specific tune, not B580, and mostly a runtime-param/shader-optimisation fork rather than a new offload mechanism.
- **thecodacus/llama.cpp** — MoE expert cache (VRAM-resident hot experts) for `qwen35moe`/`qwen4exp`/`deepseek2`/`laguna`; reports Qwen3.8-Flash-Next 177B UD-IQ3_XXS 16.6 → 24.4 tok/s with cache+MTP; plus prefill branches that are **CUDA-only** (`GGML_CUDA_REGISTER_HOST`, `GGML_SCHED_PREFETCH_EXPERTS`) [9].
- **neurall/llama.cpp** — GPU-resident LRU expert cache extending csantiago78's upstream PR #27861 ("GPU-resident LRU cache for host-offloaded MoE expert weights"); `--cpu-moe --moe-expert-cache -1` [10].
- **ParmesanParty/llama.cpp** — per-layer hot-expert cache with a dual MUL_MAT_ID path; **explicitly CUDA-only**: "the cross-backend async copy infrastructure is stubbed as NULL on non-CUDA backends (Metal, Vulkan, SYCL, etc.), so the cache refuses to engage without CUDA" [11].
- **hflong240/CatLlamaCpp** — "CatEngine" fork streaming selected experts from disk (SSD→RAM→VRAM); builds list Vulkan and SYCL, but the primary target is CUDA and there is no Arc/Intel evidence in the README [12].
- Pattern: every genuinely *new* expert-cache mechanism is CUDA-first, usually CUDA-only; the two forks with Arc paths just reproduce stock `-ncmoe` (SYCL) or tune Vulkan shaders (B390). No B580-specific expert-offload fork was found.

**LM Studio (item 4) — has the toggle, Arc evidence is weak.** Since 0.3.23 LM Studio ships "Force MoE expert weights onto CPU or GPU" in advanced load settings, and its own blog says it "is utilizing the same underlying technology as `llama.cpp`'s `--n-cpu-moe`" [13]. LM Studio runs Arc through the Vulkan llama.cpp runtime (no native Intel backend), and multiple A770 owners report the Vulkan runtime showing "Error surveying hardware" / "0 GPUs detected" and silently falling back to CPU [S3]. No B580-specific expert-offload tok/s figure was found. So: works in principle via Vulkan on Arc, unproven in practice, no measured Arc number. GGUF, OpenAI-compatible server present.

**Ollama (item 4) — no user-facing expert offload, but Vulkan is now default.** Ollama 0.30 enabled Vulkan by default for AMD and Intel devices and re-aligned with upstream llama.cpp (secondary press; [S4][S5]). But Ollama does **not** expose `--n-cpu-moe`: PR #16688, which plumbed `num_cpu_moe` through to `llama-server --n-cpu-moe N`, was **closed** as "superseded by #16958 which fixes the root cause (wrong KV cache estimate in GraphSize for SWA models) rather than adding a manual flag" [15]. So today Ollama places MoE by whole-layer auto-offload only — you cannot keep experts on CPU while attention stays on GPU except through auto-placement. Community Arc support is a real but out-of-tree path: `eleiton/ollama-intel-arc` builds a native SYCL `libggml-sycl.so` against the official Ollama binary (no IPEX-LLM), or runs stock Ollama over Vulkan [16]; it warns SYCL ops are incomplete for hybrid SSM/attention models (qwen3next) which fall back to CPU. No Arc MoE-offload tok/s found.

**Qwen3.8-Flash-Next / qwen35moe outside llama.cpp + Strata (item 5) — one CUDA-only engine, one private vLLM build, rest are llama.cpp forks.** Intel's own `llm-scaler` issue #649 (fetched) is the authoritative statement: checking vLLM main at `c39076feff`, "no `qwen4_exp` in the model registry… The architecture only exists in a vendor private dev build (`vllm/vllm-openai:qwen38-flash-next`, CUDA-only, no XPU variant)"; and on XPU it "runs today only via llama.cpp (PR #27742, `qwen4exp` arch): 4x Arc Pro B70, 262K context, q8_0 KV, **~29 t/s decode**, PLE tables in host RAM" [5]. Skeptical flag: vLLM issue #54593 [3] reports someone running Qwen3.8-Flash-Next on "vLLM main, Intel XPU" — that contradicts #649's "not upstream", so #54593 is likely on a vendor/fork build; treat its numbers as indicative, not upstream-reproducible. Beyond llama.cpp/Strata: **ninfer-offload** (CUDA-only, §item 1) and the **vLLM private CUDA build** (#649) are the only non-llama.cpp engines with Flash-Next support; SGLang XPU does **not** list `qwen4_exp` and its MoE offload is CUDA-only [6]. Additional llama.cpp-family Arc data points for Flash-Next: `bbeartheancient/flashnext-harness` and `jablyden77` both run it on **2× Arc Pro B70 via llama.cpp SYCL** — jablyden77 reports short-context decode ~**21–22 tok/s**, ~14.9 tok/s near 57K context, with `--n-gpu-layers 47` [S6]. Best published Arc Flash-Next number remains the 4× B70 ~29 t/s in [5]. No `qwen35moe` engine outside llama.cpp family was found.
